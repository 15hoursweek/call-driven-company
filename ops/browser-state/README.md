# browser-state — ブラウザ手続きの状態ファイル

セッションをまたいでブラウザ手続き（申請フォーム・アカウント手続き等）を引き継ぐための置き場。

## 背景（なぜタブではなくファイルか）

claude-in-chrome MCP拡張のタブグループはセッション単位で、別セッション（前回の定期実行・本人が進めたタブ）の既存タブにはアタッチできない。一方、MCPはユーザーの通常Chromeプロファイル内で動くため、cookie・サーバーセッション（ログイン状態・CAPTCHA通過状態がcookieに紐づくサイトならそれも）はプロファイル全体で共有される。したがって「タブを引き継ぐ」のではなく、**手続きの現在地と入力値をファイルに残し、次のセッションが新規タブで同じURLを開いて復元する**方式を取る（URL＋フィールド＋値の記録から navigate → find/read_page → form_input で入力済み状態を再現できる）。

## 規約

- 1手続き1ファイル。`{YYYYMMDD}_{手続きの要点}.md`（日付は手続き開始日）
- 手続きが完了したらファイルを削除する（git履歴に残る）
- **書いてよいもの**: URL、手順の現在地、フォームの入力値（氏名・住所・電話・メール等、既にdocs内の準備ドラフトにある情報）、次にやること、制約
- **書いてはいけないもの**: パスワード・トークン・カード番号・2FAコード等の認証情報（RUNBOOKの禁止事項）
- ファイル構成（見出し）: `状態`（現在地と最終更新）/ `再開手順`（URL・入力値・操作列）/ `制約`（CAPTCHA・本人作業の位置、無人実行の可否）

## 使い方

- **中断する側**: 手続きを途中で止めるとき（CAPTCHA・2FA・承認待ち等）、その時点のURL・入力済みの値・残りの操作をここに書く。本人作業が要るなら `user_todo/` に依頼を作り、この状態ファイルを参照させる
- **再開する側**: 状態ファイルの `再開手順` に従い、新規タブでURLを開き form_input で入力を復元して続きから進める。ログイン状態・CAPTCHA通過はcookie次第（サイトごとに `制約` に記録する）
- 本人がブラウザ操作（CAPTCHA等）をした直後に続きを進める場合は、**同じ対話セッション内で**新規タブから再開するのが最も確実
