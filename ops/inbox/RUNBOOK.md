# 定期実行 RUNBOOK（リポジトリ更新検知＋最低毎時）

あなたは無人セッションとして起動された。人間は見ていないので質問はできない。
判断に迷うものは実行せず、`docs/user_todo/`(下記)にファイルとして残すこと。
全体像は `docs/LOOP_DESIGN.md`(正本: GitHub `GITHUB_USERNAME/docs`)を参照(このRUNBOOKは③と④を担当)。

## 前提

- 打ち合わせの決定はチャットが正本リポジトリのmdに直接反映する(`ai_todo/` へのTODOファイル作成・`IDEA_` ファイル作成・`user_todo/` のファイル作成/削除など)。冒頭のsyncで `docs/` に届く
- 会社の理念・ルールは `docs/COMPANY.md`。事業構成は `CLAUDE.md` 参照
- `docs/` は正本リポジトリ(GitHub `GITHUB_USERNAME/docs`)の作業コピーで、`docs/ops/sync-docs.sh`(自動コミット→pull --rebase→push)で同期する。**処理の最初と最後に必ず実行すること**
- ファイルの移動・削除・編集はローカルの `docs/` で行う。最後の sync で GitHub に反映される

## 手順

### 1. 振り分け

`docs/` 直下にある未振り分けの `.md` をファイル名プレフィックスで移動する(チャットが最初から置き場所に作っている場合は移動不要):

- `IDEA_...` → `docs/idea/` へ移動
- `{YYYYMMDD}_{状態}_...` 形式で状態が `未着手`・`要再試行`・`人間待ち` → `docs/ai_todo/` へ移動
- `{YYYYMMDD}_PENDING_...` → `docs/user_todo/` へ移動
- その他 → そのまま

`docs/user_todo/` へ登録する際は `{YYYYMMDD}_PENDING_{要点}.md` を1件1ファイルで作成し、既に同件のファイルがあれば作成しない（重複防止）。本文には依頼内容と関連ファイルを書く。

### 2. TODO実行

`docs/ai_todo/` は1ファイル1TODOで、状態はファイル名(`{YYYYMMDD}_{状態}_{要点}.md`。`未着手` / `完了` / `要再試行` / `人間待ち`)で管理する。日付は作成日で変更せず、状態変更は状態部分のリネームで行う。定義の正本は `docs/LOOP_DESIGN.md` の③(ここには写さない)。

状態が `未着手` または `要再試行` のファイルのうち、次を満たすものだけ実行する(`人間待ち` のファイルは触らない。状態プレフィックスのないファイルは `未着手` とみなす):

- ローカルのファイル操作・コード作成・分析・文書作成で完結する(ブラウザ操作を要するタスクは、TODOが明示的に指示しており「やらないこと」の禁止事項に当たらない場合のみ実行してよい)
- 破壊的でない(既存の人間作成ファイルの削除・大幅書き換えを伴わない。TODOが明示的に指示している場合は可)
- 開発TODO(`developer/` 配下のアプリ開発)は、開発→テスト→ビルド→GitHubへのpush→**TestFlight配信まで**実行してよい(リリース手順は `~/.claude/skills/` の testflight-upload / appstore-release / appstore-first-release スキルに従う)。**App Store審査提出は、TODOに「審査提出まで」と明記されている場合のみ**行う。明記がなければ提出せず、提出待ちを `docs/user_todo/` に残す

実行したTODOは状態に応じてファイルをリネームする。**実行中のTODOの本文の背景・経緯の記述は消さず残すこと**(何をやろうとしたTODOかの文脈を失わない)。
**`完了` になったTODOはファイルごと削除する**(最後の sync で正本側にも反映される。実行内容は下記の記録に残り、必要なときは git 履歴から参照できる)。

失敗したTODOは原因に応じた状態にリネームし、本文に失敗理由を併記する。いずれの場合もファイルは削除しない:

- `要再試行`(一時的なネットワークエラー、ビルドの不安定さなど、再試行で通る可能性がある失敗) → 次回の実行で再試行される。人間の判断・対応が必要なものは `docs/user_todo/` にも登録する
- `人間待ち`(認証エラー・ログイン切れ・支払い・二要素認証など、人間にしかできない対応が必要な失敗) → 再試行はせず**1回で `人間待ち` にする**。`docs/user_todo/` に対応依頼のファイルを作成する(既に同件があれば重複作成しない)。以後の実行では対象外になる(解除は人間側・チャットがファイル名の状態部分を `未着手` に戻すことで行い、CLIは解除しない)

### 3. ルーティン実行

`docs/routine/ROUTINE_hourly.md` に列挙されたタスクを**毎回すべて**、TODOと同じ実行基準で実行する。他の頻度の `ROUTINE_*.md` はこの定期実行では触らない(それぞれ同じ頻度のlaunchdジョブが1対1で処理する)。ROUTINEファイル自体は削除・チェックせず、実行記録はログに残す。

### 4. 記録・報告

- 実行内容の記録はローカルの `docs/ops/inbox/logs/run-YYYY-MM-DD.md` に書く(正本リポジトリには置かない)
- **人間の判断・対応が必要なことがあった場合だけ**、`docs/user_todo/` に `{YYYYMMDD}_PENDING_{要点}.md` を作成する(要判断のタスク、エラーなど。なければ何も書かない)

## やらないこと(禁止)

- 次に挙げたもの以外の外部への公開・送信(SNSへの投稿・予約投稿、noteの公開、メール送信など)。認められているのは: 開発TODOの「GitHubへのpush」「TestFlight配信」、そして**TODOに「審査提出まで」と明記されている場合のみ**の「App Store審査提出」
- `docs/COMPANY.md` の理念・ルール部分の変更(TODOが明示的に指示している場合を除く)
- secrets・認証情報に触れる操作
- 指示のない正本リポジトリ上のファイル削除(完了TODO削除を除く)
