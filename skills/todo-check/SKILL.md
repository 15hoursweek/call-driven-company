# TODOチェック

## 0. 準備

この会話でまだ読んでいなければ、GitHubの正本リポジトリ `GITHUB_USERNAME/docs`（mainブランチ）をGitHub MCPで読む：

1. `COMPANY.md`
2. `LOOP_DESIGN.md`（プレフィックス定義・TODOの状態定義）
3. `user_todo/` のディレクトリ一覧（未消化の人間側タスク。1TODO=1ファイルで、ファイル名 `{YYYYMMDD}_PENDING_{要点}.md` から内容が分かる。詳細が必要なファイルだけ本文を読む）

## モードA: 新規TODOの登録

- 内容・期限・対象事業（あれば）を確認して簡潔に整理する。
- TODOは1ファイル1TODOで、状態はファイル名で管理する（`{YYYYMMDD}_{状態}_{要点}.md`。日付は作成日で以後変更せず、状態変更は状態部分のリネーム。状態定義の正本はLOOP_DESIGN.mdの③）。新規TODOのファイル名は `{YYYYMMDD}_未着手_{要点}.md` とし、要点はファイル名だけで内容が分かる粒度にする。
- **`ai_todo/` に新規ファイルとして直接作成する**（GitHub MCPで作成。コミットメッセージは内容の一行要約。本文には背景・経緯・関連ファイルを書く）。作成前に `ai_todo/` の一覧を読み、既存TODOと同件・矛盾がないか確認する。作成したTODOは毎時の定期実行が実行する。

## モードB: user_todo/の消化（人間→AIへボールを返す）

目的: 人間にしかできない判断・作業をこの打ち合わせの場で完了させ、続きをAIが実行できる状態にする。

1. user_todo/の未消化ファイルを一覧提示し、どれを消化するか確認する。
2. 項目ごとに、**人間の判断・入力をその場で引き出す**：
- 判断待ちの項目 → 選択肢と判断材料を整理して提示し、決めてもらう
- 情報待ちの項目 → 必要な情報をインタビューで聞き取る
- 作業待ちの項目（実機操作・支払い等） → 完了したか確認し、結果を聞き取る
3. 消化できた項目は**AIが続きを実行できるTODOに変換**する：
- 人間の判断結果・提供情報を本文に含め、`ai_todo/` の新規ファイル（`{YYYYMMDD}_未着手_{要点}.md`）として作成する。対応する `人間待ち` 状態のファイルが `ai_todo/` に既にある場合は、本文に結果を追記して状態部分を `未着手` にリネームする
- user_todo/の該当ファイルはその場で削除する
4. その場で消化できなかった項目は残し、理由（何待ち）を明確にする。

## 安全弁

- 人間の判断を代行しない。選択肢と材料の整理まではするが、決めるのは本人。
- user_todo/のファイルを勝手に消化済み扱いにしない。本人の確認が取れたものだけ変換する。
- `ai_todo/` の既存TODOやその他の既存ファイルを、本人の確認・決定なしに書き換え・削除しない。
- user_todo/にTODOを積むときは `{YYYYMMDD}_PENDING_{要点}.md` を1件1ファイルで作成する（同件があれば重複作成しない。関連するAI側の作業があれば本文に `関連: ai_todo/の該当ファイル名` を書く）。
